# Requirements Document

## Introduction

Haunted Homelab is an AI sysadmin agent for a personal homelab that runs services such as Plex, Pi-hole, and other Docker containers. The agent reads real-time container status, container logs, and host metrics through a pluggable data-source layer. A browser web app lets the user ask questions in natural language. All AI usage goes through OpenRouter with a single OpenRouter API key: an LLM model on OpenRouter writes the replies in a spooky "ghost in the machine" persona, and a text-to-speech model on OpenRouter speaks them aloud. The agent also watches the homelab, raises "haunting" alerts as pop-ups (for example "A strange process is haunting the CPU"), and can suggest restarting or stopping a container, which runs only after the user confirms in the UI.

The primary use is recording a demo video. A simulator data source can stage incidents on demand so the demo can show alerts and recovery without breaking real services. System data (metrics, container names, log excerpts) is sent to OpenRouter, which forwards it to the upstream provider of the configured LLM and TTS models. The user has accepted this.

## Glossary

- **Haunted_Homelab**: The whole system: the Backend, the Web_App, and the Agent.
- **Backend**: The server process that hosts the Agent, the Monitor, the Data_Source, the LLM_Client, the TTS_Client, and the Action_Executor, and serves the Web_App.
- **Web_App**: The browser user interface, made up of the Chat_Page, the Status_Panel, and Alert_Popups.
- **Chat_Page**: The Web_App view where the user types questions and reads and hears Ghost_Replies.
- **Status_Panel**: The Web_App view that shows live Host_Metrics and the state of every Container.
- **Alert_Popup**: A pop-up notification in the Web_App that shows a Haunting_Alert.
- **Agent**: The Backend component that answers user questions, summarizes logs, writes Haunting_Alert text, and creates Action_Proposals by calling the LLM_Client with homelab data.
- **Ghost_Persona**: The spooky "ghost in the machine" speaking style that the Agent applies to every Ghost_Reply and Haunting_Alert.
- **Ghost_Reply**: A text answer from the Agent to a user question, written in the Ghost_Persona.
- **Data_Source**: The common interface through which the Backend reads Containers, Container_Logs, and Host_Metrics, and through which the Action_Executor restarts or stops Containers.
- **Docker_Source**: The Data_Source implementation that reads from the Docker Engine API and from the host operating system.
- **Simulator_Source**: The Data_Source implementation that returns synthetic homelab data and stages Incidents on demand.
- **Container**: A Docker container reported by the Data_Source, identified by name, with a state (running, exited, restarting, paused, or created), CPU usage percentage, and memory usage. Services such as Plex and Pi-hole appear as Containers.
- **Container_Log**: Timestamped log lines emitted by a Container.
- **Host_Metrics**: Host CPU usage percentage, memory used and total, and disk used and total for each mounted filesystem.
- **Snapshot**: A point-in-time collection of all Containers and the Host_Metrics, with the time the data was read.
- **Incident**: A synthetic fault staged by the Simulator_Source. Incident types are: cpu_spike, memory_leak, disk_full, container_crash, and container_restart_loop.
- **Monitor**: The Backend component that reads a Snapshot on a fixed interval and evaluates Alert_Rules.
- **Alert_Rule**: A condition evaluated by the Monitor against a Snapshot that, when true, produces a Haunting_Alert.
- **Haunting_Alert**: A proactive notification generated by the Monitor and worded by the Agent in the Ghost_Persona, with a severity (warning or critical), the affected Container or host resource, and the time detected.
- **OpenRouter**: A hosted gateway that gives access to cloud LLM and text-to-speech models from many upstream providers through one API and one API key.
- **LLM_Model**: The OpenRouter model slug (for example `openai/gpt-4o-mini`) that the LLM_Client uses for text generation.
- **TTS_Model**: The OpenRouter model slug (for example `openai/gpt-4o-mini-tts-2025-12-15`) that the TTS_Client uses for speech generation.
- **TTS_Instructions**: Optional text in the Configuration that describes the spoken delivery of the Ghost_Persona voice, such as tone and pacing.
- **LLM_Client**: The Backend component that sends prompts to the LLM_Model through OpenRouter and returns generated text.
- **TTS_Client**: The Backend component that sends text to the TTS_Model through OpenRouter and returns audio.
- **Action**: An operation on a single Container. Supported Actions are restart and stop.
- **Action_Proposal**: A suggestion from the Agent to perform one Action on one named Container, shown in the Web_App with Confirm and Cancel controls.
- **Action_Executor**: The Backend component that runs a confirmed Action_Proposal through the Data_Source.
- **Configuration**: Settings read by the Backend at startup from environment variables or a config file, including one OpenRouter API key, the LLM_Model, the TTS_Model, the TTS voice identifier, the optional TTS_Instructions, the selected Data_Source, polling interval, and Alert_Rule thresholds.

## Requirements

### Requirement 1: Pluggable data-source interface

**User Story:** As a homelab owner, I want all system data to come through one common data-source interface, so that I can switch between my real Docker host and a simulator without changing the rest of the system.

#### Acceptance Criteria

1. THE Data_Source SHALL provide operations to list all Containers, read the most recent Container_Log lines for a named Container up to a requested line count, read Host_Metrics, restart a named Container, and stop a named Container.
2. WHEN the Backend starts, THE Backend SHALL select the Docker_Source or the Simulator_Source according to the data source setting in the Configuration.
3. IF the data source setting in the Configuration names an unknown Data_Source, THEN THE Backend SHALL exit at startup with an error message that lists the valid Data_Source names.
4. THE Agent, the Monitor, the Status_Panel, and the Action_Executor SHALL obtain homelab data and perform Actions only through the Data_Source interface.

### Requirement 2: Docker data source

**User Story:** As a homelab owner, I want the agent to read my real containers, logs, and host resources, so that the ghost reports on what is actually happening in my homelab.

#### Acceptance Criteria

1. WHEN the Docker_Source lists Containers, THE Docker_Source SHALL return the name, state, CPU usage percentage, and memory usage of every Container reported by the Docker Engine API, including stopped Containers.
2. WHEN the Docker_Source reads Container_Logs for a named Container, THE Docker_Source SHALL return the most recent log lines from the Docker Engine API, up to the requested line count, with a timestamp on each line.
3. WHEN the Docker_Source reads Host_Metrics, THE Docker_Source SHALL return host CPU usage percentage, memory used and total in bytes, and disk used and total in bytes for each mounted filesystem.
4. WHEN the Docker_Source receives a restart or stop request for a named Container, THE Docker_Source SHALL send the matching restart or stop command to the Docker Engine API and return success or the error reported by the Docker Engine API.
5. IF the Docker Engine API is unreachable, THEN THE Docker_Source SHALL return a data-source-unavailable error that names the configured Docker Engine API endpoint.
6. IF a request names a Container that the Docker Engine API does not report, THEN THE Docker_Source SHALL return a container-not-found error that includes the requested name.

### Requirement 3: Simulator data source and staged incidents

**User Story:** As a demo presenter, I want to stage incidents on demand, so that I can record alerts and recovery in a demo video without breaking my real services.

#### Acceptance Criteria

1. WHILE the Simulator_Source is the selected Data_Source, THE Simulator_Source SHALL report a default set of Containers that includes Containers named plex and pihole, all in the running state with CPU usage below 50 percent and memory usage below 50 percent of host memory.
2. WHILE the Simulator_Source is the selected Data_Source, THE Simulator_Source SHALL generate Container_Log lines for each running Container at least once every 10 seconds.
3. WHILE the Simulator_Source is the selected Data_Source, THE Web_App SHALL show an incident control that lets the user stage any Incident type and clear all staged Incidents.
4. WHEN the user stages a cpu_spike Incident, THE Simulator_Source SHALL report host CPU usage of at least 95 percent and add a Container whose name suggests an unknown process with CPU usage of at least 90 percent.
5. WHEN the user stages a memory_leak Incident for a named Container, THE Simulator_Source SHALL increase the memory usage of that Container on each read until host memory usage reaches at least 95 percent.
6. WHEN the user stages a disk_full Incident, THE Simulator_Source SHALL report disk usage of at least 95 percent on the root filesystem.
7. WHEN the user stages a container_crash Incident for a named Container, THE Simulator_Source SHALL report that Container in the exited state and append error lines describing the crash to the Container_Log of that Container.
8. WHEN the user stages a container_restart_loop Incident for a named Container, THE Simulator_Source SHALL report that Container in the restarting state and append a repeated startup failure line to the Container_Log of that Container.
9. WHEN the Simulator_Source receives a restart request for a Container affected by a staged Incident, THE Simulator_Source SHALL clear that Incident and report the Container in the running state.
10. WHEN the user clears all staged Incidents, THE Simulator_Source SHALL return every Container and the Host_Metrics to the default values defined in criterion 1 of this requirement.
11. WHEN the Simulator_Source receives a stop request for a named Container, THE Simulator_Source SHALL report that Container in the exited state.

### Requirement 4: Monitoring and alert detection

**User Story:** As a homelab owner, I want the agent to watch my homelab continuously, so that I learn about problems without having to ask.

#### Acceptance Criteria

1. WHILE the Backend is running, THE Monitor SHALL read a Snapshot from the Data_Source at the polling interval set in the Configuration, with a default of 5 seconds.
2. WHEN host CPU usage in consecutive Snapshots stays above the CPU threshold for at least the CPU duration, THE Monitor SHALL raise a Haunting_Alert for the host CPU, with a default CPU threshold of 90 percent and a default CPU duration of 30 seconds.
3. WHEN host memory usage in a Snapshot is above the memory threshold, THE Monitor SHALL raise a Haunting_Alert for host memory, with a default memory threshold of 90 percent.
4. WHEN disk usage of any mounted filesystem in a Snapshot is above the disk threshold, THE Monitor SHALL raise a Haunting_Alert for that filesystem, with a default disk threshold of 90 percent.
5. WHEN a Container changes from the running state to the exited state between two consecutive Snapshots, THE Monitor SHALL raise a critical Haunting_Alert for that Container.
6. WHEN a Container is in the restarting state in a Snapshot, THE Monitor SHALL raise a critical Haunting_Alert for that Container.
7. WHEN a Container appears in a Snapshot that was absent from the previous Snapshot and that Container uses more than the CPU threshold, THE Monitor SHALL raise a warning Haunting_Alert for that Container.
8. WHILE an Alert_Rule condition remains true for the same Container or host resource, THE Monitor SHALL raise at most one Haunting_Alert for that Alert_Rule and that Container or host resource.
9. WHEN an Alert_Rule condition that produced a Haunting_Alert becomes false, THE Monitor SHALL mark that Haunting_Alert as resolved and notify the Web_App.
10. IF the Data_Source returns an error while the Monitor reads a Snapshot, THEN THE Monitor SHALL raise one critical Haunting_Alert stating that the Data_Source is unavailable and continue polling at the configured interval.

### Requirement 5: Proactive haunting alerts

**User Story:** As a homelab owner, I want proactive alerts to pop up and be spoken in a ghostly voice, so that problems feel like the machine itself is warning me.

#### Acceptance Criteria

1. WHEN the Monitor raises a Haunting_Alert, THE Agent SHALL write the alert message in the Ghost_Persona and include the affected Container name or host resource and the measured value that triggered the Alert_Rule.
2. WHEN the Agent finishes writing a Haunting_Alert message, THE Web_App SHALL show an Alert_Popup with the message, severity, and detection time within 2 seconds.
3. WHEN the Web_App shows an Alert_Popup while voice output is enabled, THE Web_App SHALL play the spoken audio of the Haunting_Alert message produced by the TTS_Client.
4. WHEN the user dismisses an Alert_Popup, THE Web_App SHALL remove that Alert_Popup from view.
5. IF the LLM_Client fails to return alert text within 10 seconds, THEN THE Agent SHALL use a predefined Ghost_Persona alert template filled with the affected Container name or host resource and the measured value.
6. WHEN a Haunting_Alert is resolved, THE Web_App SHALL show an Alert_Popup in the Ghost_Persona stating that the affected Container or host resource has recovered.

### Requirement 6: Natural-language chat

**User Story:** As a homelab owner, I want to ask questions in plain language such as "Is the Plex server feeling okay?", so that I can check my homelab without reading dashboards.

#### Acceptance Criteria

1. WHEN the user submits a question on the Chat_Page, THE Agent SHALL read a current Snapshot from the Data_Source and send the question, the Snapshot, and the recent Chat_Page conversation to the LLM_Client.
2. WHEN a user question names a Container, THE Agent SHALL include up to the most recent 100 Container_Log lines of that Container in the request to the LLM_Client.
3. WHEN the LLM_Client returns a response, THE Chat_Page SHALL display the Ghost_Reply below the user question.
4. THE Agent SHALL produce Ghost_Replies that state the Container states and metric values exactly as reported in the Snapshot.
5. IF a user question names a Container that the Data_Source does not report, THEN THE Agent SHALL reply in the Ghost_Persona that no Container with that name exists and list the names of the Containers that exist.
6. WHILE the Agent is waiting for the LLM_Client, THE Chat_Page SHALL show a waiting indicator.
7. IF the LLM_Client returns an error or exceeds 30 seconds, THEN THE Chat_Page SHALL display a Ghost_Persona error message stating that the reply failed and keep the user question available for resubmission.
8. THE Chat_Page SHALL keep the conversation history for the current browser session.

### Requirement 7: Log summarization

**User Story:** As a homelab owner, I want the ghost to summarize container logs for me, so that I can understand what a service has been doing without reading raw log lines.

#### Acceptance Criteria

1. WHEN the user asks the Agent to summarize the logs of a named Container, THE Agent SHALL read up to the most recent 200 Container_Log lines of that Container and send the lines to the LLM_Client with a summarization instruction.
2. WHEN the LLM_Client returns a log summary, THE Agent SHALL return a Ghost_Reply that lists error and warning events found in the log lines, with the timestamp of each listed event.
3. IF the Container_Log of the named Container contains no lines, THEN THE Agent SHALL reply in the Ghost_Persona that the Container has produced no log lines.

### Requirement 8: Ghost persona

**User Story:** As a demo presenter, I want every reply and alert to sound like a ghost in the machine while staying accurate, so that the demo is entertaining and still trustworthy.

#### Acceptance Criteria

1. THE Agent SHALL instruct the LLM_Client to write every Ghost_Reply and Haunting_Alert message in the Ghost_Persona, using spooky metaphors to describe system state.
2. THE Agent SHALL limit each Ghost_Reply intended for speech to 120 words.
3. THE Agent SHALL limit each Haunting_Alert message to 40 words.
4. THE Agent SHALL keep every Container name and metric value in a Ghost_Reply or Haunting_Alert message identical to the value in the source Snapshot or Container_Log.

### Requirement 9: Text-to-speech output

**User Story:** As a demo presenter, I want ghost replies to be spoken aloud in a spooky voice, so that the demo video has an audible ghost character.

#### Acceptance Criteria

1. WHEN the Chat_Page displays a Ghost_Reply while voice output is enabled, THE Web_App SHALL play the audio for that Ghost_Reply produced by the TTS_Client.
2. THE TTS_Client SHALL use the voice identifier set in the Configuration for every audio request.
3. THE Web_App SHALL provide a control that enables and disables voice output, with voice output enabled by default.
4. WHEN new audio is requested while earlier audio is still playing, THE Web_App SHALL queue the new audio and play the new audio after the earlier audio ends.
5. IF the TTS_Client returns an error or exceeds 15 seconds, THEN THE Web_App SHALL display the text without audio and show an indicator that voice output failed for that message.
6. THE TTS_Client SHALL request audio in mp3 format for every audio request.
7. WHERE TTS_Instructions are set in the Configuration, THE TTS_Client SHALL send the TTS_Instructions text with every audio request.

### Requirement 10: Live status panel

**User Story:** As a homelab owner, I want a live status panel, so that I can see the health of all containers and the host at a glance.

#### Acceptance Criteria

1. THE Status_Panel SHALL display host CPU usage percentage, memory usage percentage, and disk usage percentage for each mounted filesystem.
2. THE Status_Panel SHALL display the name, state, CPU usage percentage, and memory usage of every Container in the latest Snapshot.
3. WHEN the Monitor reads a new Snapshot, THE Status_Panel SHALL show the new values within 2 seconds.
4. WHILE a Container or host resource has an unresolved Haunting_Alert, THE Status_Panel SHALL mark that Container or host resource with the severity of the Haunting_Alert.
5. IF the Web_App loses the connection to the Backend, THEN THE Status_Panel SHALL show a disconnected indicator and the time of the last received Snapshot.

### Requirement 11: Confirmed container actions

**User Story:** As a homelab owner, I want the ghost to suggest restarting or stopping a container and run the action only after I confirm, so that the agent can help fix problems without acting on its own.

#### Acceptance Criteria

1. WHEN the Agent determines that restarting or stopping a Container would address a reported problem, THE Agent SHALL create an Action_Proposal that names the Action, the Container, and the reason.
2. WHEN the Agent creates an Action_Proposal, THE Web_App SHALL display the Action_Proposal with a Confirm control and a Cancel control.
3. THE Agent SHALL limit Action_Proposals to the restart and stop Actions.
4. WHEN the user clicks the Confirm control of an Action_Proposal, THE Action_Executor SHALL run the proposed Action on the named Container through the Data_Source.
5. THE Action_Executor SHALL run an Action only in response to a user click on the Confirm control of a pending Action_Proposal.
6. WHEN the user clicks the Cancel control of an Action_Proposal, THE Web_App SHALL mark the Action_Proposal as cancelled and disable both controls of that Action_Proposal.
7. WHEN the Action_Executor finishes an Action, THE Agent SHALL report the result in a Ghost_Reply on the Chat_Page, stating success or the error returned by the Data_Source.
8. IF the user clicks the Confirm control of an Action_Proposal more than 5 minutes after the Action_Proposal was created, THEN THE Action_Executor SHALL reject the Action and THE Web_App SHALL show that the Action_Proposal has expired.
9. WHEN an Action_Proposal is confirmed, cancelled, or expired, THE Backend SHALL reject any later confirmation of that Action_Proposal.

### Requirement 12: Configuration and secrets

**User Story:** As a homelab owner, I want to configure the OpenRouter API key and settings through environment variables or a config file, so that I can run the agent without putting secrets in code.

#### Acceptance Criteria

1. WHEN the Backend starts, THE Backend SHALL read the OpenRouter API key, the LLM_Model, the TTS_Model, the TTS voice identifier, the optional TTS_Instructions, the Data_Source selection, the Docker Engine API endpoint, the polling interval, and the Alert_Rule thresholds from environment variables or a config file.
2. WHERE a setting is defined both as an environment variable and in the config file, THE Backend SHALL use the environment variable value.
3. IF the OpenRouter API key is missing or empty at startup, THEN THE Backend SHALL exit with an error message that names the missing setting.
4. THE Backend SHALL keep the OpenRouter API key on the Backend and exclude the OpenRouter API key from every response sent to the Web_App and from every log line written by the Backend.

### Requirement 13: Data sent to cloud providers

**User Story:** As a homelab owner, I want to know and limit what system data leaves my machine, so that I accept the privacy trade-off knowingly.

#### Acceptance Criteria

1. THE Agent SHALL send to the LLM_Client only the user question, the recent Chat_Page conversation, Snapshot fields, and Container_Log lines limited by the line counts in Requirements 6 and 7.
2. THE TTS_Client SHALL send to OpenRouter only the text of the Ghost_Reply or Haunting_Alert message to be spoken, the TTS_Model, the configured voice identifier, the TTS_Instructions when set, and the requested audio format.
3. THE Web_App SHALL display a notice stating that system data is sent to OpenRouter and to the upstream provider of each configured model, naming OpenRouter, the LLM_Model, and the TTS_Model.
